# vpc-endpoints

Runs in a **workload account** via a platform pipeline. Creates VPC Interface
and Gateway endpoints inside the workload VPC for private connectivity to AWS
service APIs, so traffic to services like S3, STS, ECR, or SSM doesn't have
to hairpin through NAT or a Transit Gateway. Wraps the `vpc-endpoints` shared
module, translating tier names (`subnet_ids_by_tier`, `route_table_ids`) into
the raw subnet/route-table IDs the module expects.

Independent of whether the account has a Transit Gateway at all: the module
only needs a VPC ID plus, per endpoint, either subnets (Interface) or route
table IDs (Gateway). It works the same whether `vpc` is attached to
the landing-zone TGW or the VPC is fully isolated with no network plane —
this project has no dependency on TGW attachment state, unlike
`vpc-routes`.

## Endpoints

Configured via the `endpoints` map, one entry per AWS service. Each entry
resolves to exactly one `aws_vpc_endpoint`. See the field reference and the
`Gateway` / `Interface` distinction in the
[`vpc-endpoints` module README](../../shared/modules/vpc-endpoints/README.md)
— the fields here are the same except `subnet_ids` and `route_table_ids` are
replaced with tier names:

| Field | Notes |
|---|---|
| `subnet_tier` | Interface only. A key in `subnet_ids_by_tier` (from `vpc`). |
| `route_table_tiers` | Gateway only. Keys in `route_table_ids` (from `vpc-routes`) whose tables get the service's prefix-list route. |

```hcl
endpoints = {
  "s3" = {
    type              = "Gateway"
    route_table_tiers = ["app", "data"]
  }
  "sts" = {
    type               = "Interface"
    subnet_tier        = "app"
    security_group_ids = [aws_security_group.vpce.id]
  }
}
```

## Security groups

The `vpc-endpoints` module itself creates none — it only attaches whatever
`security_group_ids` an entry supplies (BYO, same convention as
`rds-postgresql`'s `security_group_id`). This project adds one layer on top,
following the EOC precedent this is based on: any Interface entry that omits
`security_group_ids` joins a shared fallback security group
(`security_groups.tf`), created lazily — only when at least one entry needs
it, skipped entirely when every entry brings its own.

By default the shared group opens **all ports/protocols** rather than a
fixed port — the module makes no assumption about which port an endpoint
answers on, because endpoint services don't all use 443 (Amazon MSK, for
example, uses 9092/9094/9096/9098 depending on auth mode). Set
`security_group_ports` (and optionally `security_group_protocol`, default
`tcp`) to narrow this down when you know exactly which ports every endpoint
sharing the group actually needs — e.g. `[443]` for an all-HTTPS set, or
`[443, 9098]` to add MSK/IAM alongside HTTPS ones. This is an explicit
opt-in; leaving it empty keeps the no-assumptions default.

Source scoping is via `security_group_cidrs` (default `0.0.0.0/0`) and
`security_group_source_security_group_ids`. Its `name` is left unset by
default so AWS assigns one, avoiding any collision with an existing group;
set `security_group_name` only if a fixed name is required downstream.

Mix and match freely: give some entries their own `security_group_ids` for
per-service isolation and leave others unset to share the fallback group.

### Implementation notes (`security_groups.tf`)

- The group (and its rules) is created via `count`, only when at least one
  Interface entry has an empty `security_group_ids` — a configuration where
  every entry brings its own creates nothing here.
- Rules are generated by `setproduct(ports, cidrs)` /
  `setproduct(ports, source_security_group_ids)` when `security_group_ports`
  is set, so N ports × M sources becomes N×M single-purpose ingress rules
  (one CIDR/SG and one port per rule, matching the
  `aws_vpc_security_group_ingress_rule` best practice over inline blocks).
  When `security_group_ports` is empty, it's one rule per CIDR/SG with
  `ip_protocol = "-1"` and no port instead.
- No egress rule is created — the client side of an interface endpoint
  doesn't need one ([AWS guidance](https://repost.aws/knowledge-center/security-network-acl-vpc-endpoint)),
  and an unrestricted egress rule would trip `CKV_AWS_382` for no benefit.
- The `aws_security_group.shared` resource carries a `checkov:skip` for
  `CKV2_AWS_5` ("security group attached to another resource"): it *is*
  attached, via `local.endpoints` → `module.vpc_endpoints`'s
  `aws_vpc_endpoint.security_group_ids`, but that indirection through a
  local map and a module boundary is invisible to checkov's static graph.

## Route table dependency (Gateway endpoints)

Gateway endpoints need `route_table_ids`, normally
`vpc-routes.route_table_ids`. That project fails fast until the TGW
attachment is `available` (see its README), so a pipeline step chained
strictly behind it inherits that gate even for endpoints that have nothing to
do with the TGW. If Gateway endpoints must be creatable before TGW
acceptance — or the VPC has no TGW attachment at all — pass `route_table_ids`
from a source that isn't gated on attachment state, or configure
`vpc-routes` for the no-TGW case (tracked separately). Interface-only
configurations have no such dependency.

## Organization-scoped endpoint policy

Opt-in via `organization_id`. When set, every endpoint whose service supports
endpoint policies gets a baseline policy denying access to principals outside
the organization (`aws:PrincipalOrgID`), unless the entry sets its own
`policy_json`. `@landing-zone/workload-parameters` does not currently publish
an organization ID — wiring this requires adding it there first (`workload-ous`
already outputs `organization_id` in the landing zone; it just isn't
re-published to platform pipelines yet).

## Pipeline usage

```yaml
- project: vpc-endpoints
  source: vpc-endpoints
  target: test-rico
  depends_on: [vpc-routes]
  inputs:
    - name: vpc.vpc_id
      var: vpc_id
    - name: vpc.subnet_ids_by_tier
      var: subnet_ids_by_tier
    - name: vpc-routes.route_table_ids
      var: route_table_ids
  outputs:
    - name: endpoint_ids
    - name: gateway_prefix_list_ids
    - name: shared_security_group_id
```

Drop the `vpc-routes` input and `depends_on` entry entirely for an
Interface-only configuration (no Gateway endpoints) — `route_table_ids`
defaults to `{}`.

## What does NOT belong here

- Per-service security group rules beyond the shared fallback — a caller
  with custom per-service port requirements supplies its own
  `security_group_ids` on that entry instead of relying on the fallback.
- Route table ownership — owned by `vpc-routes`; this project only
  associates Gateway endpoints with route table IDs it's given.
- Anything not exposed via `aws_vpc_endpoint` (e.g. Route 53 Resolver
  endpoints for hybrid DNS — see `network-resolver` in the network plane).
